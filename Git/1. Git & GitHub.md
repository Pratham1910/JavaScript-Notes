## 1. The Big Picture: What is Version Control?

  

Imagine you are writing a book. You save "Version 1". You make changes and save "Version 2". Later, you realize Version 1 was better. Without version control, you've lost it.

  

**Git** keeps a history of every single change ever made. You can travel back in time, branch off to try new ideas, and merge those ideas back when they work.

## 2. Setup & Configuration

  

Before you start, tell Git who you are. This information is attached to your commits.

  

```bash

git config --global user.name "Your Name"

git config --global user.email "you@example.com"

git config --global core.editor "core --wait"

git config --global core.autocrlf "input"

git config --global -e

```

### What it does

These two commands tell Git **who you are**. Git uses this information to record the **author** of every commit you make.

---

## 1. `git config --global user.name "Your Name"`

Example:

```bash
git config --global user.name "Prathamesh Naik"
```

### What it does

It sets your **name** for all Git repositories on your computer.

Every commit you create will contain something like:

```text
Author: Prathamesh Naik
```

You can verify it:

```bash
git config --global user.name
```

Output:

```text
Prathamesh Naik
```

---

## 2. `git config --global user.email "you@example.com"`

Example:

```bash
git config --global user.email "prathamesh@example.com"
```

### What it does

It sets the **email address** associated with your commits.

Each commit stores:

```text
Author: Prathamesh Naik <prathamesh@example.com>
```

Verify it:

```bash
git config --global user.email
```

Output:

```text
prathamesh@example.com
```

---

## Why are these important?

Every Git commit contains metadata such as:

- Author name
    
- Author email
    
- Date and time
    
- Commit message
    
- Commit hash
    

For example:

```text
commit 7a9c3e9d...
Author: Prathamesh Naik <prathamesh@example.com>
Date:   Sat Jul 4 10:30:15 2026 +0530

    Add login page
```

This information helps identify who made each change.

---

## What does `--global` mean?

The `--global` flag means these settings apply to **all Git repositories** on your computer for your user account.

```
Computer
│
├── Project A
├── Project B
├── Project C
└── Project D

All use:
Name  = Prathamesh Naik
Email = prathamesh@example.com
```

Without `--global`, the setting only applies to the current repository.

For example:

```bash
git config user.name "Office Account"
git config user.email "office@company.com"
```

These values are saved in that repository's `.git/config` file and override the global settings only for that project.

---

## Where are these settings stored?

When you run:

```bash
git config --global user.name "Prathamesh Naik"
git config --global user.email "prathamesh@example.com"
```

Git writes them to your global configuration file:

- **Windows:** `C:\Users\<YourUsername>\.gitconfig`
    
- **Linux/macOS:** `~/.gitconfig`
    

The file looks like:

```ini
[user]
    name = Prathamesh Naik
    email = prathamesh@example.com
```

---

## How to see all your Git settings

```bash
git config --global --list
```

Example output:

```text
user.name=Prathamesh Naik
user.email=prathamesh@example.com
core.editor=code --wait
core.autocrlf=input
init.defaultbranch=main
```

---

### Summary

|Command|Purpose|
|---|---|
|`git config --global user.name "Your Name"`|Sets your name for all Git commits on this computer.|
|`git config --global user.email "you@example.com"`|Sets the email associated with your Git commits.|
|`git config --global --list`|Displays all global Git configuration settings.|

> **Tip:** If you use GitHub, GitLab, or Bitbucket, it's generally a good idea to use the same email address that is associated with your account. That allows the platform to correctly attribute your commits to your profile.

It tells Git to use **Visual Studio Code** as the default editor whenever Git needs you to write something.

For example:

- Commit messages
    
- Interactive rebase
    
- Merge conflict messages
    
- Tag messages
    

Without this setting, Git may open Vim or Nano.

### Why `--wait`?

When Git launches VS Code, it needs to wait until you're finished editing.

Without `--wait`

```bash
git commit
```

Git opens VS Code...

Immediately thinks you're done...

Commit gets aborted or uses an empty message.

With

```bash
code --wait
```

Git waits until you close the file.

Example:

```bash
git config --global core.editor "code --wait"
```

Now

```bash
git commit
```

opens

```
COMMIT_EDITMSG
```

You type

```
Added login feature
```

Save → Close

Git continues.

## 2. `git config --global core.autocrlf "input"`

This is about **line endings**.

Different operating systems use different characters for a new line.

### Windows

```
CRLF
```

(Carriage Return + Line Feed)

Represented as

```
\r\n
```

---

### Linux / macOS

```
LF
```

Represented as

```
\n
```

---

### Why is this a problem?

Suppose you create a file on Windows.

Git sees

```
Hello\r\n
World\r\n
```

Someone on Linux has

```
Hello\n
World\n
```

Git thinks every line changed.

---

### `core.autocrlf=input`

```bash
git config --global core.autocrlf input
```

Meaning:

- When you **commit**, Git converts CRLF → LF.
    
- When you **check out**, Git leaves files as LF.
    

So the repository always stores Linux-style (`LF`) line endings.

This is recommended if you:

- Use WSL
    
- Work in Linux
    
- Develop cross-platform
    
- Use VS Code with LF endings
    

---

### Other options

#### `true`

```bash
git config --global core.autocrlf true
```

Checkout:

```
Repository (LF)
↓

Windows (CRLF)
```

Commit:

```
CRLF

↓

LF
```

Best for Windows users using Windows-native tools.

---

#### `input`

```
Checkout:

LF

↓

LF
```

Commit:

```
CRLF

↓

LF
```

Good for Linux/macOS and many developers using WSL.

---

#### `false`

Git does nothing.

Whatever line endings exist stay unchanged.

## 3. `git config --global -e`

This opens your global Git configuration file in the configured editor.

Equivalent to opening:

```
~/.gitconfig
```

or on Windows

```
C:\Users\<username>\.gitconfig
```

If you previously ran

```bash
git config --global core.editor "code --wait"
```

then

```bash
git config --global -e
```

opens `.gitconfig` in VS Code.

You might see something like:

```ini
[user]
    name = Prathamesh Naik
    email = example@email.com

[core]
    editor = code --wait
    autocrlf = input

[init]
    defaultBranch = main
```

You can edit these settings directly, save, and close the editor.

---

```bash

```

View a specific setting:

```bash

```

Remove a setting:

```bash

```

```bash

```

## 3. The Basic Workflow (Add, Commit, Push)

  

### The Three Stages

1.  **Working Directory:** Files you are currently editing.

2.  **Staging Area (Index):** Files you have "marked" to be saved.

3.  **Local Repository:** The saved "snapshot" on your computer.

  

### The Commands

```bash

# 1. Check status

git status

  

# 2. Add files to Staging Area

git add index.html          # Add specific file

git add .                   # Add everything

  

# 3. Commit (Save locally)

git commit -m "Added a cool navigation bar"

  

# 4. Push (Upload to GitHub)

git push origin main

```

## 4. Branching & Merging

  

Branches allow you to work on new features without breaking the "Main" (production) code.

  

```bash

# Create a new branch

git branch feature-login

  

# Switch to that branch

git checkout feature-login

# OR (Short way to create and switch)

git checkout -b feature-login

  

# Merge feature-login back into main

git checkout main

git merge feature-login

```

## 5. Collaboration on GitHub (PRs & Forks)

  

When working with others, you don't usually push directly to `main`.

  

### Pull Requests (PRs)

1.  Push your feature branch to GitHub.

2.  Open a **Pull Request** on the GitHub website.

3.  Teammates review your code, leave comments, and eventually **Merge** it.

  

### Forking

If you don't have access to a repository, you **Fork** it (create your own copy on GitHub), make changes, and send a PR to the original owner.

## 6. Resolving Merge Conflicts

  

A conflict happens when two people change the **same line** in the **same file**. Git doesn't know which one to keep.

  

### How to Fix It:

1.  Git will mark the file:

    ```text

    <<<<<<< HEAD

    I like Blue

    =======

    I like Red

    >>>>>>> feature-branch

    ```

2.  Open the file and manually choose which line to keep (or combine them).

3.  Remove the `<<<<`, `====`, and `>>>>` markers.

4.  `git add <file>`

5.  `git commit -m "Resolved merge conflict"`

## 7. Advanced: Git Stash

  

**Scenario:** You are half-way through a feature, but you need to switch branches to fix an urgent bug. You aren't ready to commit yet.

  

**Solution:** `git stash`

  

```bash

# Temporarily "hide" your changes

git stash

  

# Check your stashes

git stash list

  

# Switch branches, fix the bug, come back...

  

# Bring your changes back

git stash pop

```

## 8. Advanced: The Power of `git reset` & `git revert`

  

### `git revert` (Safe)

Creates a NEW commit that does the exact opposite of a previous commit. **Use this on shared/remote branches.**

```bash

git revert <commit-hash>

```

  

### `git reset` (Dangerous)

Deletes commits from history as if they never happened. **Use ONLY on your own local branches.**

```bash

git reset --hard <commit-hash>  # DANGER: Deletes all uncommitted work!

```

## 9. Advanced: Force Pushing & Amending

  

### Amending a Commit

Forgot to add a file to your last commit? Use `--amend`.

```bash

git add forgotten-file.txt

git commit --amend --no-edit

```

  

### Force Pushing (`--force`)

If you've rewritten your history (like using `reset` or `amend`) and try to push, GitHub will reject it. You must force it.

  

**DANGER:** This can overwrite your teammate's work if they've pushed changes since your last pull.

  

```bash

# The "Safe" Force Push (Recommended)

git push --force-with-lease

```

*Note: `--force-with-lease` checks if someone else has pushed new code before overwriting.*

## 10. Working with Teams: The Flow

  

A standard team workflow:

1.  `git pull origin main` (Get latest code).

2.  `git checkout -b my-feature` (New branch).

3.  Make changes + `git add` + `git commit`.

4.  `git push origin my-feature`.

5.  Open Pull Request on GitHub.

6.  Address review comments.

7.  Merge into `main`.

## 11. What to Do (Compulsory)

  

*   ✅ **Commit Often:** Small, frequent commits are easier to manage than one giant commit.

*   ✅ **Write Good Messages:** `Fixed bug` is bad. `Fixed login timeout issue on mobile` is good.

*   ✅ **Pull Regularly:** Always pull before you start working to avoid conflicts.

*   ✅ **Use .gitignore:** Always include a `.gitignore` file to prevent sensitive files (like `.env` or `node_modules`) from being uploaded.

*   ✅ **Verify Before Committing:** Run `git diff` or `git status` to see what you are actually saving.

  

---

  

## 12. What NOT to Do (Avoid)

  

*   ❌ **NEVER commit secrets:** Do not push API keys, passwords, or `.env` files to GitHub.

*   ❌ **Don't force push to `main`**: This is the fastest way to break a project for the whole team.

*   ❌ **Don't use `git add .` blindly:** You might accidentally add a temporary file or a massive log file.

*   ❌ **Don't ignore conflicts:** Resolving them early is much easier than waiting a week.

*   ❌ **Don't share a single GitHub account**: Everyone should have their own.
